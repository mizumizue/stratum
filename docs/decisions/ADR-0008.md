## Content

### Context
これまでの設計やドキュメントにおいて、`src/` 配下の製品コードがあたかも「TypeScript / Node.js」や特定のアーキテクチャパターン（ヘキサゴナル、レイヤード、Clean Architecture 等）を採用することを前提としているかのような表現が散見されていた。しかし、当リポジトリにおける本尊は **`src/` に配置される「製品（プロダクト）」そのもの** であり、開発フレームワーク（ForgOS）および品質地層・トレーサビリティ分析（Stratum）は **「製品を正しく・高品質に作るための支援機能」** である。製品の特性・ドメイン要件・規模に応じて、最適なアーキテクチャや言語（Go, Rust, Python, TypeScript 等）は千差万別である。開発フレームワークや品質保証ツールが、プロダクト自身の内部設計指針やコード構造にまで干渉・限定することは、設計の自由度を奪い保守性を損なう。

### Decision
`src/` 配下に配置される製品コードについて、**特定のアーキテクチャや特定のプログラミング言語に一切限定せず、プロダクト自体の設計指針には一切関わらない（完全不干渉・中立）** 方針を決定し、以下の原則を徹底する。

1. **プロダクト設計指針・アーキテクチャの完全な自由**:
   - `src/` 配下の製品コードは、いかなる特定のアーキテクチャパターン（MVC, レイヤード, オニオン, クリーン, ヘキサゴナル, モジュラーモノリス等）にも限定されない。
   - プロダクト自身の設計指針、モジュール分割、クラス設計、ディレクトリ構成は、製品開発チームの完全な裁量に委ねられる。
2. **言語・技術スタックの中立性**:
   - プロダクトの特性に最適な任意の言語（Go, Rust, Python, TypeScript, Java, C++ 等）およびフレームワークを採用可能とする。
3. **What vs How の厳格遵守（仕様は What、製品コードは How）**:
   - 開発FW（ForgOS）および品質機能（Stratum）が扱うのは「仕様・契約・受入基準（What: `docs/`）」と「客観的な合否エビデンス（`reports/test-results.json`）」のみである。
   - 内部構造や実現手段（How）である製品コードの設計指針・コード配置には一切干渉しない。
4. **非侵襲な観測性 & 多言語品質検証・静的解析の分離**:
   - トレーサビリティ分析や可視化ダッシュボードの都合で、製品のコード配置や設計方針が歪められることを厳格に防止する。
   - FW自身のドキュメントスキーマ検査（`validate-docs.ts`）と、製品コード（`src/` 配下）の静的解析・リンター（`ProductLinter` / `./bin/stratum lint-product`）を明確に責務分離する。
   - テスト結果インジェスト（`TestReportIngester` / `./bin/stratum ingest-report`）を通じて、Python (pytest), Go (go test), Rust (cargo test), Java (JUnit) 等の多言語テストレポートを決定論的に取り込み可能とし、製品の言語選定を束縛しない。

### Consequences
- あらゆるアーキテクチャスタイル、あらゆるプログラミング言語を採用したプロダクトに対して、開発FW（ForgOSのモード駆動開発）と品質地層分析（Stratum）を同一の規律で安全に適用できる。
- 「ツールの都合で製品コードの構造が制約される」「特定フレームワークやTypeScriptが暗黙に強制される」といった本末転倒が完全に排除され、製品本位のアーキテクチャが実現される。
- 本リポジトリのツール自身が採用している内部実装構造（例: Core/Application/Infrastructureのヘキサゴナル構造など）は、あくまでツール自身の一実装例に過ぎず、開発対象プロダクトのアーキテクチャを縛るものではないことが明確化される。
