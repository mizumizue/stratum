# テスト駆動開発 (TDD)

TDD は赤 → 緑 → リファクタリングのループである。このスキルは、そのループが価値あるテストを生むためのリファレンスである: 良いテストとは何か、テストの置き場、アンチパターン、ループの規則。各セクションはすべてのサイクルに適用される — ループの前と最中に参照し、後ではない。

本プロジェクトの仕様は `docs/`（REQ, SPEC, DSN, TC）に定義されている。テスト名やインターフェース語彙はプロジェクトのドメイン言語と一致させる。

## 良いテストとは

テストは実装の詳細ではなく、**公開インターフェース**を通じて振る舞いを検証する。内部構造に依存しないため、リファクタリングに耐えうる。

例は [tests.md](tests.md)、モックの指針は [mocking.md](mocking.md) を参照。

## テスト境界 — テストの置き場

テストは **公開インターフェース**（アプリケーション境界）に置く: 内側の実装詳細に手を入れず、外から振る舞いを観察する。内部のプライベートメソッドや配線はテストしない。

使う語: 公開インターフェース、アプリケーション境界、テスト境界。使わない語: 継ぎ目、シーム、seam。

## アンチパターン

- **実装結合** — 内部コラボレータを過剰にモックし、プライベートメソッドをテストする。振る舞いが変わっていないのに内部リファクタで壊れる。
- **同語反復的** — アサーションがコードと同じロジックで期待値を再計算する。期待値は独立した正 — 既知のリテラル、スペック — から来なければならない。
- **エビデンスの作文（ADR-0006 違反）** — テスト結果を Markdown に手作業や LLM の作文で書き込むこと。テスト結果はテストランナーによる決定論的レポート（`reports/test-results.json`）で証明する。

## ループの規則

- **緑の前に赤。** 失敗するテストを先に書き、通すのに十分なコードだけを書く。
- **1スライスずつ。** 1サイクルに公開インターフェース 1 つ、テスト 1 つ、最小実装。
- **リファクタリング。** テストが緑になった後、重複を排除し責務を整理する。

## Implement セッション完了

TDD サイクルを回し、単体・結合テストが緑（Pass）になり、`reports/test-results.json` に客観的エビデンスが記録されていること。
