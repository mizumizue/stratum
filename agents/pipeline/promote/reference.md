# Promote — 分解リファレンス

ステップ 3（PRD を分解する）で使う。SKILL.md の手順の代替ではない。

## PRD の読み方

Source は次の節構成を持つ機能 PRD とする（`specs/source/<feature-slug>/spec.md`）。欠落節は「不足」としてゲート／Audit に載せる。中身をインタビューで埋めない。

| 節 | 取り込むもの |
|----|--------------|
| 課題（Problem Statement） | 背景。決め事本文には短く残すか、関連リンクに留める |
| 解決策（Solution） | 用語の種、ユースケース概要の種 |
| ユーザーストーリー（User Stories） | アクター責務、ユースケースの基本／例外フロー |
| 実装上の決定（Implementation Decisions） | **決め事の主原料（What）**。公開インターフェース・境界・拒否条件。内部構造・手順は取り込まない |
| テスト上の決定（Testing Decisions） | 決め事の検証可能性・主たる公開インターフェースの裏付け |
| スコープ外（Out of Scope） | 決め事の境界、またはユースケースの対象外 |
| 補足（Further Notes） | 関連 issue。**sandbox・実装パスは Source／sandbox 側に残し、取り込んだ L2/L3 には書かない。Source 自体は取り込み後に削除** |

プロトタイプ由来の形（インターフェース要約）は、散文より正確なら決め事に要点だけ残す。

## 節 → 種別

| 種別 | 置き場 | PRD からの主な入力 |
|------|--------|-------------------|
| glossary | `glossary/` | Solution・Implementation の固有名詞 |
| actors | `actors/` | User Stories の「〜として」 |
| decisions | `decisions/` | Implementation + Testing + Out of Scope |
| usecases | `usecases/` | User Stories を導線単位に束ねたもの |

L3 が既定。技術横断だけが残る内容は L2。アプリ業務と技術横断が混ざる草案は、業務側を L3・横断規範を L2 に分け、衝突を一覧する。

## 公開インターフェース／テスト境界

Implementation Decisions から、単体テストで検証する **公開インターフェース**（またはアプリケーション境界）を拾う。既存の高い境界を新規より優先する。新しい境界が必要なら、できるだけ利用者・呼び出し側に近い位置で提案し、決め事に一文で残す。

使う語の例: 公開インターフェース、アプリケーション境界、テスト境界、API。  
使わない語: 継ぎ目、シーム、seam（ユーザー向け説明・承認カード・決め事の見出しで禁止）。

## 承認カード

ステップ 5 で必ず出す。ユーザーがコピペ／一言で返せる形にする。ゲート表や差分のあとに置く。

### 必須の出し方

1. 先に「何を承認するか」を 2〜4 行の平文で要約する。
2. 選択肢を出す前に、論理的に比較する（何が違うか・何が同じか・トレードオフ）。
3. 各選択肢の本文に、**その案で実際に起きること**を書く。ラベルだけ（「A で承認」）で終わらせない。差分のない案は出さない。
4. **推奨**と**次点**を必ず明示する。それぞれに理由を書く（優先度が高い理由が先）。
5. **返信例**を番号付きで提示する。各案は「そのまま送れる一文」にする。
6. カスタム承認の書き方を一行添える。
7. 未返信・「あとで」は非承認として止める。
8. 「継ぎ目」「シーム」は出さない。テスト境界は「公開インターフェース」等で書く。

### テンプレ（必要に応じて項目を埋める）

```markdown
## 承認のお願い（Promote）

これから仕様フォルダ（`specs/L2|L3`）へ書き込む内容の採否をお願いします。
未承認のまま書き込みはしません。

### 今回の要点
- Source: …
- 書き込み先: …
- 主な変更: …
- 提案成熟度: …

### テストする公開インターフェース ※該当時
- 主: …
- （あれば副）: …

### 選択肢の比較
| 案 | やること（具体） | やらないこと | 向く状況 |
|----|------------------|--------------|----------|
| A | … | … | … |
| B | … | … | … |

### 推奨と次点
- **推奨: <案名>** — 理由: …
- **次点: <案名>** — 理由: …

### 返信してください（どれか一つ、またはカスタム）

1. **A で承認** — <A の具体内容を一文で繰り返す>
2. **B で承認** — <B の具体内容を一文で繰り返す>
3. **差し戻し** — まだ書かない。直してほしい点: （続く）
4. **保留** — 今回は Promote を止める

カスタム例: `推奨どおり B。成熟度だけ draft`
```

選択肢は 2〜4 個。比較表なし・推奨なし・理由なしの承認カードは不合格（出し直す）。

## 成熟度

| 操作 | 成熟度 |
|------|--------|
| 初回取り込み・追記 | 原則 `draft`（人間が別指定したときのみそれ以外） |
| draft → stable / confirmed | Promote ゲート承認後のみ |

## 書かないもの

- L1（Steward 以外）
- 機能 PRD の複製を L2/L3 直下に置くこと（正本の置き場は種別ファイル）
- L2/L3・hub への **Source リンク／旧パス／コミット参照**（取り込み後に Source を削除する。憲法 §2.5・ゲート）
- **L2/L3 からのソース参照**（`product/` 実装・`sandbox/` パス、実装ファイル名。L1 憲法 §2.5）
- **How・内部構造・作業手順（Order）**（モジュール分割、アルゴリズム、手順書。憲法 §2.8）

## Source 削除（必須）

ステップ 6 完了直後に当該 `specs/source/<feature-slug>/` を削除する（任意ではない）。`sandbox/` は連動しない。
