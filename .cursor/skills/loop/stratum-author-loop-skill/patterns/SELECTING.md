# 型の選定（ユーザーには型名を選ばせない）

目的・困りごと・成功条件のヒアリング結果から、エージェントが型を1つ選ぶ。  
ユーザーへは **平易な言い方＋理由** だけ示し、一言承認を取る。型のメニューは出さない。

## 選定表

| シグナル（ヒアリングで拾う） | 選ぶ型 | ユーザーへの言い方（例） |
|------------------------------|--------|-------------------------|
| バグ・壊れている・遅い・再現したい | **DIAG** | まず「その不具合で赤になる検査」を作ってから直す回り方 |
| 機能追加・テストがある／書ける・品質を担保したい | **RGR** | 先に失敗するテストを書き、通してから整える回り方 |
| 数値・スコア・ベンチで良し悪しが決まる実験 | **GV** | 小さく変えては点数で残す／捨てる回り方 |
| 同じ方針で何度も自動反復・放置して進めたい | **RALPH** | 同じ指示を繰り返し、ディスク上の進捗で育てる回り方 |
| 文章・提案・翻訳など、採点基準はあるがテストしにくい | **EO** | 作る役と見直す役を分けて交互に直す回り方 |
| 方針・要件・意思決定がまだ枝分かれしている | **GRILL** | 質問で枝を一本ずつ潰してから手を動かす回り方 |

## 衝突時

1. **意思決定が未解決**が主なら GRILL を先に（他型の前段）。
2. バグが主なら DIAG を優先（RGR より先に赤シグナル）。
3. それ以外は「成功条件が機械で判定できるか」→ できるなら RGR/GV、できないなら EO。
4. 迷ったら候補1つだけ推奨し、理由を1文で示す。ユーザーに型名の比較表は出さない。

## ワークフロー工程での位置づけ

型は **`loop-eng` 実行時**のレシピである。工程に具体ループスキルを割り当てるときは型を省略してよい。  
実行手段の選び方（スキル / loop-eng / ペルソナ空）は [`../../loop-workflow/STAGE-EXEC.md`](../../loop-workflow/STAGE-EXEC.md) を正本とする。

- [ ] 型IDが1つに決まっている
- [ ] 平易な言い方と理由をユーザーに示し、一言承認を得ている
